## 1. 状态与刷新

> **导读**：ArkUI 的刷新模型是「**读时登记依赖**」——状态变量只有在 `build()`（含其 `@Builder`）被**读过**时，才与组件建立依赖关系。本章大多数坑都源于把其它框架（React / Compose / Flutter）的直觉套了过来。

### 1.1 `@State` 只在 `build()` 读过它时才登记依赖 —— 「改个 tick 刷新」是无效写法

**现象**：页面写成下面这样，UI 永远不更新：

```ts
@State tick: number = 0;                       // 监听器里 this.tick += 1
build() { ... Text(this.store.error) ... }     // build 只读 store 字段，从不读 tick
```

日志里能看到网络请求成功、状态也确实变了，但界面一动不动。

**根因**：`store.error` 是普通对象字段（非 `@Observed` / `@State`），不参与观察；`tick` 虽然自增了，但 `build()` 里从未读取它 → 框架没有登记依赖 → 不标记脏 → 不重建。**没被读过的状态变量自增等于空操作。**

**修法**：

1. 监听器里把数据**拷进 `@State` 字段**，`build()` 只读这些字段：

   ```ts
   @State messages: TimelineMessage[] = [];
   aboutToAppear() { this.store.onChange(() => { this.pull(); }); }
   private pull(): void { this.messages = this.store.messages.slice(); }
   build() { ... ForEach(this.messages, ...) ... }   // 读的是 @State
   ```

   注意**数组要用 `slice()` 换成新引用**：原地 `push()` 不会触发刷新。

2. 路由 / 登录态这类全局标量，摊平成 `AppStorage` 的**字符串键**，由根页面用 `@StorageLink('key')` 直读；不要「把整个对象塞进 `AppStorage`、由页面调 `Router.current()` 取值」。

3. 条件渲染的分支只读 `@State`（否则分支永不重建，见 1.3）。

**判据**：想知道某个状态到底生不生效，**不要看代码里有没有赋值，要在 `build()` 里搜这个变量名**——搜不到就是没依赖。

### 1.2 `@Builder` 的值参数与 `if` 分支不会因「内容变了但条件值没变」而重建

**现象**：流式输出时，用户气泡正常，**助手气泡完全不出来**。页面写的是：

```ts
if (messages.length > 0) { ListItem() { this.msgRow(last) } }
```

**根因**：条件值 `messages.length > 0` 恒为真 → 分支不会被重新求值 → 尾条永远停在**首次创建时**的那个（当时还是空对象）。值参数 `@Builder` 同理：参数是「值」而不是「引用」时，只要外层不重建，内层就不重跑。

**修法**：拆成两个 `ForEach`——

- 「已完成消息」用**稳定 key**（`m.id`），内容变化不重建，避免整列表抖动；
- 「活动尾条」用**单元素数组 + 随内容变化的 key**，强制刷新。

**判据**：任何「内容会变、但承载它的条件或参数不变」的渲染路径，都要问一句：**它靠什么变？** 答案不能是「因为数据变了」。

### 1.3 参与条件渲染的状态必须是 `@State`

**现象**：一段流动光效动画「在跑但看不见」——`animateTo` 每帧都在改角度变量，屏幕上什么都没有。

**根因**：

```ts
if (this.glowOn) { 光带层 }    // glowOn 是普通成员变量，不是 @State
```

动画只改了 `@State glowAngle`，而承载它的 `if` 分支从未被创建——动画在跑，元素不存在。

**修法**：把 `glowOn` 改成 `@State`。

**附带经验**：在固定尺寸容器里做「旋转渐变光带」时，内层内容**必须给固定小尺寸**（写 `width('100%') + margin(2)` 会把光带整圈盖住），外壳用 `clip(true) + borderRadius` 裁圆角。

### 1.4 `ForEach` 的 key 必须包含「会变的内容」

**现象**（同一个根因的两个真实案例）：

| 现象 | key 哪里不够 |
| --- | --- |
| 切「进行中 / 已归档」筛选，按钮高亮变了，列表还是原来那几条 | key 用了 `${projectId}:${sessions.length}`，而两个列表的会话数恰好相同 → key 完全撞车 |
| 重命名成功后列表仍显示旧标题 | 组内**会话 id 集合**没变 → 外层 `ForEach` 复用 `ListItem` → **值参数 `@Builder` 不重跑** → 内层 `ForEach` 根本不求值 |

**根因**：`ForEach(data, itemBuilder, keyGenerator)` 的 diff **只看 key**：key 相同就复用组件、不重建。完整链条要记住——

```text
外层 key 不变 → item 复用 → 值参数 @Builder 不重跑 → 内层 ForEach 不求值
```

**修法**：把「会在不换 id 的情况下变化」的字段写进 key：

```ts
`${group.projectId}:${this.showArchived}:` +
  group.sessions.map((s) => `${s.id}:${s.title}:${s.status}:${s.updatedSeq}:${s.pinned}`).join(',')
```

**判据**：**这个列表项会不会在不换 id 的情况下改内容？** 会（重命名、状态流转、流式增长、文件大小变化、增量更新事件）就必须进 key。

### 1.5 会变的「数据字段」进 key，`@State` 标记**不要**进 key —— 这是两条相反的路

把上一条过度泛化成「什么都要塞进 key」会踩新坑。两条路径是**相反**的：

| 走哪条路 | 例子 | 怎么做 | 为什么 |
| --- | --- | --- | --- |
| **会变的数据字段** | 行内文本（来自 `@Prop` 数组的普通字段） | **必须进 `ForEach` 的 key** | 不进 key 就永不刷新 |
| **`@State` 标记** | 勾选态集合、当前选中项 id | **行内用 `this.isXxx(row)` 判，绝不要进 key** | `@State` 只要被 `build()` 读到就登记**元素级依赖**，变化直接驱动该元素重绘；塞进 key 反而让每次变化都重跑整轮 O(n) 的 key 生成（勾选态曾因此退化成 O(n²)） |

**判据**：先问「这个值变化时，我希望整行重建，还是只希望这一处重画？」——前者进 key，后者读 `@State`。

### 1.6 单例 store 的监听器必须存成**字段**才能摘除 —— 匿名箭头函数摘不掉

**现象**：页面反复进出后内存单调增长；已销毁的组件仍在被回调，甚至在已销毁的 Canvas 上重绘。

**根因**：store 是单例、`listeners` 只增不减时，页面注册必须与销毁配对，而：

```ts
// ❌ 摘不掉：offChange 内部用 indexOf 定位，匿名函数每次都是新引用
aboutToAppear(): void { this.store.onChange(() => { this.pull(); }); }
```

**修法**：

```ts
// ✅ 存成字段，注册 / 注销用同一个引用
private storeListener: () => void = () => { this.pull(); };
aboutToAppear(): void { this.store.onChange(this.storeListener); }
aboutToDisappear(): void { this.store.offChange(this.storeListener); }
```

**判据**：数一数 `onChange(` 与 `offChange(` 的调用点数量，**对不上就是漏了**。另外：全局静态控制器也要提供 `offChange`——只给 `onChange` 等于逼调用方泄漏。

### 1.7 `Tabs` + 自定义 `tabBar`：`onChange` 必须回灌选中状态

**现象**：点底栏切页，内容区正常切换，但自定义 `tabBar` 的高亮与指示器**停在冷启动那一页**；冷启动首帧却是对的。

**根因**：`Tabs({ index: this.activeIndex })` 的 `index` 只是**初值 / 受控入参**，用户点击切页**不会自动写回** `@State`；自定义 tabBar 的高亮读的正是这个 `@State`，而 `onChange` 里只调了业务切换函数、从未回灌 `activeIndex = index`。程序化 `tabsController.changeIndex()` 同样不会替你回灌。

**修法**：

```ts
onChange((index: number) => { this.activeIndex = index; /* 业务切换 */ })
```

业务切换函数保留「同值短路」防抖，回灌与 `changeIndex` 双保险收敛后不会来回打架。

**为什么容易漏**：设计文档里写了对的做法，代码却丢了回灌；而「首帧对齐」掩盖了切换路径的缺陷——**只截冷启动首帧的验证，永远发现不了它**。

### 1.8 `bindSheet` 的 `isShow` 必须是 `boolean`，且弹层要挂在**页面根节点**

**现象**：点按钮完全没反应——无报错、无崩溃、日志干净，面板就是不出现。

**根因**：SDK 签名是 `bindSheet(isShow: boolean, builder, options?)`，而代码图省事把 `@State xxxId: string` 用 `$$` 传了进去。**编译器对这类 `$$` 用法不报警**，运行期表现为永不弹层。

```ts
// ✗ 字符串当开关：点了没反应
@State actionSheetSessionId: string = '';
.bindSheet($$this.actionSheetSessionId, this.sessionActions(session), { … })

// ✓ 布尔开关 + 打开时把要渲染的字段拷成标量快照
@State showActions: boolean = false;
@State actionSheetSessionId: string = '';
@State actionSheetTitle: string = '';
.bindSheet($$this.showActions, this.sessionActions(), { … })
```

**同一个坑的第二半**：`bindSheet` 不要挂在列表的**每一行**上——所有行共享同一个组件级开关，一开就**同时弹出 N 个面板**。正解是挂到**页面根节点**一个，行只负责写开关与快照字段。

**判据**：`$$` 双向绑定要求被绑变量是可写状态且**类型与形参一致**；拿不准时先去 SDK 的 `component/*.d.ts` 里核对签名，别凭印象。

## 2. 布局与命中测试

> **导读**：ArkUI 里「看得见的」与「点得到的」是两套东西。布局正确不代表命中正确；`0 error / 0 warning` 对命中面缺陷**完全无感**。本章的核心方法是：**量几何**，而不是看截图。

### 2.1 `HitTestMode.Block` 会连子节点一起阻塞

**现象**：用户报「底部对话框点不了」——里面的输入框、按钮全部点死。

**根因**：为了拦住底下列表的滚动，给悬浮容器加了 `hitTestBehavior(HitTestMode.Block)`。而 SDK 的权威语义是：

| 取值 | 自身 | 子节点 | 兄弟节点 | 祖先 |
| --- | --- | --- | --- | --- |
| `Default` | 响应 | **响应** | 阻塞 | 不受影响 |
| `Block` | 响应 | **阻塞** | 阻塞 | 阻塞 |
| `Transparent` | 响应 | 响应 | **不**阻塞 | — |
| `None` | 不响应 | 响应 | 不阻塞 | — |

**修法**：想要「子控件可用 + 兄弟列表被挡」用 `Default`。

**判据**：`dumpLayout` 里子控件 `clickable=true`、`focused=false`，点了没反应 → 查**父链上的 `hitTestBehavior`**。

### 2.2 重叠布局里，**每个铺满的兄弟容器都参与命中测试并阻断下层**

**现象**：把顶栏改成 `Stack` 三层（铺满的标题层 + 贴左按钮组 + 贴右按钮组）之后，**侧栏完全打不开**：汉堡按钮 6 个点位真实触摸 + 连拍 5 帧 + 左缘右滑全部无反应；同排的「新建」按钮却正常（因为它在覆盖层内部）。`dumpLayout` 里按钮 `enabled` / `clickable` **均为 `true`**。

**根因**：`Stack` 后添加者在上层 ⇒ 最上层的**右按钮组 `Row`** 成了整条顶栏的触摸目标。该 `Row` 只画了两个图标按钮，但自身 `.width('100%')` **铺满整条顶栏**——**ArkUI 里「铺满但没有 `onClick` 的容器」仍然参与命中测试并阻断兄弟节点**。

**为什么第一版修不掉**：只给铺满的标题层加了 `HitTestMode.None`，漏掉了真正致命的两个按钮层（它们也铺满）。而且 `None` 的语义是「**自身**不参与命中、**子节点仍然参与**」，所以它**只对「覆盖层里全是纯展示内容」这一种情形够用**。

**修法**（两条，优先第一条）：

1. **首选「不重叠的排布」**：顶栏改回**单层 `Row` 三槽、零重叠**——左槽 / 标题槽 `.layoutWeight(1)` / 右槽，左右槽**等宽且固定** ⇒ 剩余空间的中心 = 屏幕中心 ⇒ 标题严格居中、且不随右侧按钮数量漂移。命中面天然就是按钮本身，**一个 `hitTestBehavior` 都不需要**。

   ```ts
   // ❌ 重叠布局：标题层加了 None，两个铺满的按钮组 Row 漏了
   Stack() {
     Row().width('100%')                       // 标题层（纯展示）
     Row() { /* 左按钮 */ }.width('100%')      // ← 漏了！铺满且在上层
     Row() { /* 右按钮 */ }.width('100%')      // ← 后添加 = 最上层 = 整条顶栏的触摸目标
   }
   // ✅ 不重叠：单层三槽，左右槽等宽固定
   Row() { /* 左槽 */ /* 标题槽 .layoutWeight(1) */ /* 右槽 */ }
   ```

2. **确实必须重叠时**：**每一个铺满的兄弟容器都显式给出 `hitTestBehavior`**，写完后**对每个可点元素重跑真实触摸回归**。

**可复用教训**：**重写布局时必须先确认「命中测试面」与旧布局等价**。旧布局（单层 `Row`）天然不重叠、命中面就是按钮本身；新布局引入了**新的、铺满整屏的命中面**。构建期 `0 error / 0 warning` 对这类缺陷完全无感。

### 2.3 `Stack` 子节点上的 `.align()` 不生效 —— 悬浮控件会落到**容器正中**

**现象**：给内容区右上角挂一个悬浮按钮，写成子节点链上的 `.align(Alignment.TopEnd) + .margin({...})`。`BUILD SUCCESSFUL`、`WARN 0 / ERROR 0`，截图那个位置本来就是空的，**看不出异常**；一量 bounds，按钮在**屏幕正中**。

**根因**：`Stack()` 未写 `alignContent` 时默认 `Center`，子节点上的 `align` 根本不被采纳。

**修法**：对齐写在**容器**上——`Stack({ alignContent: Alignment.TopEnd })`，子节点只留 `margin`。

**判据**（按容器类型分）：

- `Scroll` 这类**只有一个孩子**的容器：`.align()` 控起始位置，是常规写法；
- `Stack`（多孩子叠加）：一律用构造参数 `alignContent`，**不要**在子节点上写 `.align()`。

**取证要求**：新挂 / 移动任何悬浮控件后，**必须 dump 一次看 bounds**——编译期与肉眼都不可靠，只有几何是硬的。

### 2.4 「按内容撑开」的容器里，子节点别写 `width('100%')`

**现象**：消息气泡里的附件行只显示了文件名，右侧的「体积」整格不见；`dumpLayout` 里**连节点都查不到**，看起来像根本没渲染。

**根因**：父容器是 `constraintSize({maxWidth:'86%'})` + 无固定宽（按内容撑开），子 `Row` 却写了 `.width('100%')`——百分比在这个父容器里解析成**比父容器更宽**的值，整行向右溢出，最后一个子项被推到裁剪区外，于是**既不建节点也不上报**。

**修法**：

- 内层去掉固定宽，按内容宽度走；
- 会变长的子项给上限：`constraintSize({ maxWidth: 200 })` + `maxLines(1)` + 省略号。

**顺带澄清**：给末尾子项加 `flexShrink(0)` **解决不了**——它管的是「有富余空间时是否被压缩」，而这里是「行本身比父容器宽」。

**第二形态（图片）**：`Image().width('100%')` 在同一类气泡里会把**整条气泡**撑出屏幕——左侧文字被裁、图片右半边看不见。更阴的是它**设备相关**：真机（density 2.97）恰好没超、看着正常，模拟器（density 3.5）立刻现形。所以图片要用**按屏幕算出来的上限**而不是百分比：

```ts
const metrics = display.getDefaultDisplaySync();   // 记得 try/catch，否则 ArkTS 告警
const widthVp = metrics.width / (metrics.densityPixels > 0 ? metrics.densityPixels : 1);
this.imageMaxWidth = Math.floor(widthVp * 0.72);
```

**判据**：**节点在 `dumpLayout` 里查不到 → 先怀疑被挤出父容器**，把它的 `bounds` 和父容器右边界比一比。凡是「按百分比定宽」的子节点，都要在**两种密度**（真机 + 模拟器）下各看一眼。

### 2.5 用「被测元素自身的实测尺寸」给它自己做让位 ⇒ **布局反馈环**

**现象**：想让「元信息行」浮层落在标题栏之下，于是给它的容器写 `margin({ top: this.headerHeight })`，而 `headerHeight` 正是这一行自己的 `onAreaChange` 写进去的。真机实测：这一行被压成 **8px**。

**根因**：这是一个**自我指涉**的布局环——

1. `headerHeight` 由该行的 `onAreaChange` 写；
2. 该行的**位置**又由 `margin.top = headerHeight` 决定；
3. 求解过程收敛到退化不动点：**让位量 = 0、行高 = 0**。

**修法**：让位量必须**不依赖被让位元素自身**。可用来源按优先级：

1. **框架常量**：标题栏高度这类由框架给定的值；
2. **兄弟 / 父级**的实测值（它们不因你而变）；
3. **状态栏 / 导航栏**高度（从 `AppStorage` 读）。

若确实需要动态让位，`onAreaChange` 必须挂在**另一个**节点上（例如挂在内容层，而不是挂在这个浮层自己身上）。

**附带一条同源的坐标系坑**：`margin` 与 `List.contentStartOffset` 的基准都是**窗口顶 y=0**，**不是**「内容区顶（= 标题栏下沿）」：

| 传的值 | 实测落点 | 判定 |
| --- | --- | --- |
| 只算标题栏高 | 落到标题栏**底下** | ❌ |
| 状态栏高 + 标题栏高 | 正好是标题栏下沿 | ✅ |

⇒ 要让元素落在标题栏下方，必须传 `px2vp(状态栏高) + 标题栏高`。

### 2.6 「取 max」不等于「贴到底」：**目标值与上限值不能混为一谈**

**现象**：容器要给内容留底部避让。第一版写成「宿主让一份 + 容器让一份」⇒ 相加，偏大。改成 `max(真实安全区, 目标值)` 之后，**小安全区设备上看着正常，大安全区设备上却等于安全区**。

**根因**：`max(安全区, 目标)` 只在**安全区小于目标**时才等于目标；安全区一大，它就退化成**安全区**。而**安全区是系统留给自己的上界，不是内容必须退让的下界**——真机实测：底部安全区 33px，而手势条可见横线只在距底 7~13px，中间约 20px 是**死区**，压进去既不撞手势条、也不影响上滑手势命中。

**修法**：

1. **先问「有没有更精确的物理量」**：有（如手势条可见位置）就以**物理量**定目标，安全区只当参考；把「不许低于安全区」当硬约束，等于自愿多让 20px。
2. 公式里 `min()` 用来夹目标、`max()` 用来保下限，**别让前者被后者顶掉**：`padding-bottom: max(6px, min(设备上报避让, 18px))`。
3. 改完**必须在最大的那台设备上复测**：这个缺陷在小安全区设备上**不可见**。

**判据**：「内容最深可见处 → 屏幕底」的实际像素，并用像素剖面确认**手势条横线位置未变**。

### 2.7 「共用组件的折中默认值」会让**两边都不对**，而两边单看都「差不多」

**现象**：一个组件同时服务上游两个**规格不同**的控件（一个 14sp / 左右内边距 16dp，另一个 16sp / 20dp），合并后取了中间值 15sp——对前者偏大、对后者偏小，**两边都不符，而单看任何一处都像「差不多」**。

**为什么难发现**：没有对照基线时，15sp 与 14sp / 16sp 的差别肉眼几乎看不出；编译器不会报；只有**把两侧都换算成 dp 去量**（字号看文本节点的高、间距看相邻行 `y1` 之差）才会现形。

**修法**：给共用组件加**默认值等于历史外观**的样式开关（如 `textSize` / `padH` / `boldText`），由调用点各自按上游锚文传值。这样改动面最小（其余调用点零影响）。**不要**图省事去改组件的默认值——那会顺手改掉所有调用点，且没人会逐个复核。

**判据**：合并「看起来相似」的两个控件之前，先把两者的**字号 / 内边距 / 行高**并排列出来；只要有一项不同，就必须做成可覆盖的参数，而不是取中间值。

### 2.8 显示层级（面包屑 / 路径）前，必须先把绝对路径归一到**已知根**

**现象**：文件页面包屑显示成又长又重复的绝对路径，点第一节还会去请求一个不存在的相对路径。

**根因**：服务端返回的目录 `path` 是绝对路径，UI 需要的是「相对某个根」的层级，而老实现直接把绝对路径按 `/` 切开当层级用。**层级、标签、回跳路径会一起错。**

**修法**：先剥根前缀，再对余下部分切片；根那一节单独约定（例如固定用一个代表「回根目录」的路径）：

```ts
const rootNorm = root.replace(/\\/g, '/').replace(/\/+$/, '');
let relative = current.replace(/\\/g, '/');
if (rootNorm && rootNorm !== '.' && relative.startsWith(rootNorm)) relative = relative.substring(rootNorm.length);
```

**判据**：凡是「显示层级」的数据来自绝对路径，就必须先问一句「**根是什么**」；同时把「回到根」写成一个明确的约定，别指望它按相对当前目录解析。

## 3. 材质与视觉

> **导读**：官方「沉浸光感 / 液态玻璃」从 HarmonyOS 7 起有**明确的生效范围**；本章多数坑的共性是**静默无效**——不报错、不告警、像素也不动。判断「有没有生效」的唯一可靠办法是**开关前后逐像素对比**，不是肉眼、也不是看代码里写没写。

### 3.1 沉浸光感不生效的两个独立原因

**① `module.json5` 的 `module.metadata` 值必须小写**：

```json5
{ "name": "ohos.arkui.UIMaterial.state", "value": "enable" }
```

写成大写 `"ENABLE"` 会被系统**静默忽略**——真机上 `uiMaterial.getMaterialInfo().state` 仍是默认档；改小写后立刻变成 enabled。**这一个字母的差别没有任何报错。**

**② 即便开关生效、设备支持、材质等级也够，`systemMaterial` 在页面内容区仍然不生效**（HarmonyOS 7 起），详见 3.3。

**判据**：先用探针读三个量——`supported` / `state` / `level`。开启后 `state` 必须由默认档变为 enabled；**若仍为默认档，是 metadata 的写法或位置错了**（值必须小写）。

### 3.2 应用级 `UIMaterial.state = enable` **不是空闸门**

**结论（SDK 原文可逐行核对）**：打开这一行 metadata 的**真实代价**是——

1. 一批组件**默认就带材质**，哪怕你一行材质代码都没写：各类 Dialog、Toast、AlphabetIndexer、ChipGroup / Chip、Select、菜单、Toggle、SegmentButton、Slider、**`bindSheet` 半模态**、SelectionMenu，以及设置了 `copyOption` 的文本菜单；
2. 这些组件自身设的 `backgroundColor` / 模糊 / `shadow` / 边框会被材质**压过**——SDK 原文明确「材质样式优先于组件自身设置的背景色、模糊、阴影与边框」。

**修法**：

- 打开开关前，先数一遍自己用了哪些清单内组件（尤其 `bindSheet` / `bindPopup` / 各类 Dialog / `Select` / `Toggle`），逐个登记为「本轮观感会变的接入点」并复核；
- 想显式关掉某个组件的材质：传 `uiMaterial.Material.empty`（语义是 **disable**）。

#### 同名不同入口：`systemMaterial` 有**两个**，`undefined` 的语义要分别看

| 入口 | 形参 / 字段类型 | `undefined` 的语义 | 怎么关闭材质 |
| --- | --- | --- | --- |
| 通用属性 `CommonMethod.systemMaterial` | `SystemUiMaterial \| undefined` | **no-material effect**（显式无材质） | 直接传 `undefined` 即显式声明「本节点不挂材质」 |
| `Tabs` 的 `FloatingTabBarStyle.systemMaterial` | **可选字段**（不是联合 `undefined`） | 「**未配置**」⇒ 行为由框架缺省决定 | **必须**用 `uiMaterial.Material.empty` |

⇒ **同名不同入口，`undefined` 的语义按各自 SDK 原文分别成立**；引用时**必须写清是哪个入口**。在通用属性上写 `.systemMaterial(undefined)` 是**显式声明**「本节点不挂材质」，比「整行不写」更可机械核验。

### 3.3 `systemMaterial` 的真机生效范围 + 经典毛玻璃回退

**官方行为变更要点（仅对 `targetSdkVersion >= 26.0.0` 的应用生效）**：

> 弹窗类组件（各类 Dialog、SelectionMenu、AlphabetIndexer 弹窗、文本菜单）与弹窗类接口（PromptAction、Popup、Tips、菜单、半模态转场），以及 **Slider / Toggle / Select**，仍可在页面内**全部区域**生效；
> **其他组件仅在 `Navigation` / `NavDestination` 标题栏、或横向 Tabs 且 `barPosition = BarPosition.End` 的底部 TabBar 中生效。在其他区域设置沉浸光感效果不生效。**

**这解释了一个反复踩的坑**：本项目曾在三轮里把官方材质路线做到「证据确凿的 0 像素」——`state` 已 enabled、设备支持为 true、等级也是最高档，但自绘玻璃钮、设置抽屉、`bindPopup`、`Navigation` 标题栏的 ROI 逐像素差异全是 **0.0000**。当时的结论是「官方材质在本项目画不出来」；**按官方约束，那个结论只对「放在页面正文里的普通组件」成立**——它们从 HarmonyOS 7 起本来就不在生效范围内。

**配方**：

1. 先看组件**在哪**：只有①弹窗类 ②Slider / Toggle / Select ③`Navigation` / `NavDestination` 标题栏 ④横向 Tabs 的底部 TabBar 这四类位置会生效；**页面正文里的自绘容器一律不生效**（不报错、不告警）；
2. 仍需应用级开关（值必须小写）；
3. 官方建议**不要与 `backgroundColor` / `borderColor` / `borderWidth` / `shadow` 同时使用**（材质生效时会接管这些）；
4. 判据：**开关前后逐像素 MAE**。MAE≈0 不一定是「API 坏了」，先检查**组件是不是在生效范围内**；
5. 范围外只有两条路：把组件挪进允许的区域，或**放弃官方效果走自绘**（自绘需自行承担「像不像」的全部风险）。

**回退配方**：保留 `systemMaterial` + 叠**经典毛玻璃**（半透明双值底色 + 模糊 + 阴影），真机回退生效、模拟器材质仍生效。

⚠️ **模拟器不受此限制**——只跑模拟器会漏掉这个约束。

⚠️ **按钮属豁免类型，但材质会把实色洗白**：实测把品牌色渲染成近白，白字不可读，改材质色透明度或反色都无效 ⇒ **按钮不要用 `systemMaterial`**，用实色底 + 投影。

**收敛**：材质供给收敛到**唯一入口文件**（一个 `GlassMat.*` 工厂），避免每处各写一套参数。

### 3.4 底部 TabBar 的官方材质入口是 `barFloatingStyle`，**不是 `TabsOptions`**

**现象**：按印象给 `Tabs({ barPosition: BarPosition.End, index, controller, systemMaterial })` 传材质 ⇒ **编译期就红**：

```text
Object literal may only specify known properties, and 'systemMaterial' does not exist in type 'TabsOptions'.
```

**根因（SDK 原文核对）**：`TabsOptions` 的成员只有 `barPosition / index / controller / barModifier / strokeWidth / color / startMargin / endMargin`；那个 `systemMaterial?: UIMaterial.ImmersiveMaterial` 长在 **`interface FloatingTabBarStyle`** 里，挂载点是 **`TabsAttribute.barFloatingStyle(style: Optional<FloatingTabBarStyle>)`**。

**正确写法**：

```ts
Tabs({ barPosition: BarPosition.End, index: this.topTabIndex(), controller: this.tabsController }) { /* TabContent × N */ }
  .barFloatingStyle({
    barSideMargin: Space.PAGE,
    barBottomMargin: gap,
    systemMaterial: new uiMaterial.ImmersiveMaterial({ style: uiMaterial.ImmersiveStyle.THIN, materialColor: /* 半透明 */ })
  })
```

⇒ **结构性推论**：官方底部 TabBar 的材质**只有「浮动栏」这一条路**（材质字段就长在那个对象里），所以想要官方底栏材质的应用，底栏形态**必须做成悬浮 bar**；想贴底就得放弃材质。

### 3.5 官方材质会画出**带缘高光的「带」**——相邻两块各挂一层就是肉眼可见的分界

**现象**：标题栏挂着材质、下面紧贴一行内容，用户报「**标题栏和下面那条栏有明显分界**」。

**根因**：材质不只上色，还会画**缘高光**。真机空白列竖直剖面实测：

```text
一条亮线（阶跃 +93.5）        ← 材质带顶缘高光
中间一段可见的灰带
又一条亮线                    ← 材质带底缘高光  ← 用户看到的分界
```

⇒ 两块相邻区域各挂一层材质时，**两条缘高光对不齐**，接缝反而比不挂更明显。

**修法**：要「一片连续的糊化」就用纯模糊效果，不要用官方材质；且相邻两块的 `radius` / `saturation` / `brightness` / `color` 必须**逐字同值**。

**判据（可直接复用）**：**非文字行的最大行间跳变**——只扫「没有文字 / 控件的空白列」，取逐行均值的相邻差最大值。有缘高光时是 **93.5**，换成纯模糊后是 **6.6**（差 14 倍）。必须排除文字行，否则字形边缘本身就会产生几十的跳变。

#### 量化口径：分界强度

```text
分界强度 = mean(标题栏带) − mean(它正下方正文带)
⚠️ 采样必须是**左右最边缘各约 14px 的纯底色竖条**，不能取整宽 y 带
```

同一批页面、同样是「栏本体挂材质」：深色下 **+19.0**，浅色下只有 **-1.8 ~ +2.2**。换成「栏本体零材质」后，深色也是 **+0.00**。

三条可复用的教训：

1. **整宽均值会把基准页也算成「有问题」**：第一版取整宽 y 带，结果用户认可的基准页（无分界）也算出 **+14.60**，因为标题栏里那行大字把均值抬起来了。**判据的第一步是让基准读数符合已知事实**（基准无分界 ⇒ 必须≈0）；
2. **这条坑在深色下最刺眼** ⇒ **涉及材质 / 带 / 分界的验收，至少要取一次深色证据**；
3. **处置要成套**：栏本体撤材质、**光效收回到栏内控件（按钮 / 胶囊）上**；不要顺手把「内容从栏背后穿过」那套滚动效果抄到不透明布局的页面——抄过去只有副作用（见 3.6 与 4.4）。

#### 同一坑会在**别的页面复发**

第一次只改了一页，其余 9 页的「栏本体」仍挂着整行材质 ⇒ 用户第二次报同一类观感问题。**修「某一个页面」时，要顺手扫一遍同类页面。**

### 3.6 毛玻璃的**前置条件是布局**，不是属性

**现象**：给顶栏 / 底部输入区挂模糊效果却「看不出任何模糊」，于是去调 `radius`、换 API、加 alpha——**方向全错**。

**根因**：`Column { header, timeline, composer }` 里顶栏与输入区是内容层的**兄弟节点**，滚动内容永远到不了它们背后，模糊层底下只有一块纯色画布。

**修法**：先把结构改成 `Stack`——**内容层铺满整屏**，顶栏 / 输入区做**浮层**。配套两条：

| 让位方式 | 结果 |
| --- | --- |
| `List.padding({ top: headerH })` | ❌ 内容被裁在内边距里，**永远穿不过去** |
| `List.contentStartOffset(headerH)` + `contentEndOffset(composerH)` | ✅ 只是「内容起点偏移」，滚动内容照样从玻璃下穿过 |

浮层高度要**实测**（`onAreaChange`），不要写死：顶栏会随状态行增减、输入区会随附件条变化。

- ⚠️ 回调里**只在真的变了才写 `@State`**（无条件赋值会形成「改 → 重建 → 再回调」空转）；
- ⚠️ 浮层里的**铺满型兄弟容器**要给 `HitTestMode.None`（否则连空白处一起吃掉内容层的拖拽，见 2.1 / 2.2）。

**模糊 API 的选择**：用 `backgroundEffect`（`radius` / `saturation` / `brightness` + **双值玻璃色资源**）；**不用** `backgroundBlurStyle`（那是材质，自带近不透明遮罩并接管 `backgroundColor`，见 3.7）；**不用** `backdropBlur`（只有 `radius` / `grayscale`，没法按深浅色分档）。玻璃色的 **alpha 是「透不透」的唯一旋钮**。

### 3.7 `backgroundBlurStyle` 是「材质」而不是「模糊」

**现象**：想要背景模糊，写法是 `backgroundBlurStyle(Regular/Thin)`，结果「背后内容被盖住、模糊像没生效」；把 alpha 调到 4% 甚至 `Color.Transparent` 都毫无变化。

**根因**：`backgroundBlurStyle` = 模糊 **+ 一层近乎不透明的浅色遮罩**，而且**会接管 `backgroundColor`**——你调的那个背景色根本没参与渲染。

**修法**：

| 需求 | 用什么 |
| --- | --- |
| 纯模糊 | `backdropBlur(radius)` |
| 按深浅色分别调（`saturation` / `brightness` / `color`） | `backgroundEffect({ radius, saturation, brightness, color })`，它的 `color` 吃 `ResourceColor`，可直接喂双值资源 |

**附带**：`BlurOptions.grayscale` 是**色阶调整**（提亮黑 / 压暗白、黑白趋于灰），不是锐度或性能开关。

### 3.8 模糊半径会溢出组件边界

**现象**：`backgroundEffect(radius: 40)` 放在 82% 宽的面板上，模糊会去采样**面板外的清晰内容**，在右缘形成一条「糊 → 清」的**不连续带**（逐像素剖面可见）。

**修法**：半径收到与圆角同尺度即收敛；再给一条 0.5vp 的淡描边 + 柔投影，边界就从「渲染瑕疵」读成「有意的收边」。

### 3.9 `borderRadius` **不裁滤镜**；`hitTestBehavior(None)` 的节点**收不到交互态**

两条都是在「给按钮加按下反馈」时踩到的，都属于**不报错、不告警的静默失效**。

**① `borderRadius` 只裁「背景与子节点」，不裁作用在节点自身的滤镜**（`brightness` / `blur` 等）。把一个矩形节点（例如只负责布局的 `Stack` / `Column`）做按下提亮 ⇒ 整块矩形被提亮，**圆形控件外面露出四个方角亮块**。

⇒ 判据：**滤镜要挂在「自身就有被圆角裁过的背景」的节点上**（自带背景 + 圆角的组件）；或者干脆不用滤镜，改用「覆盖层 + opacity」。

**② 为了「装饰层别吃点击」而加的 `.hitTestBehavior(HitTestMode.None)`，会让该节点上的交互态永不触发**——`.stateStyles({ pressed: ... })`、`.onTouch()` 挂在装饰层上时，**状态永远停在 normal**，而且**不报错、不告警**（现象是「按下毫无反应」，极易误判为「属性不被支持」）。

⇒ 判据：**交互态必须挂在参与命中测试的那个节点上**；装饰层只负责画。典型布局：外层（可命中）挂 `.onTouch` / `.clickEffect` / `.onClick`，内层装饰用 `@State` 显式驱动自己的 `opacity` / `backgroundColor`——「**事件 + 状态 + 上色**」三件都是已文档化的绘制原语，比赌「滤镜语义 / 属性白名单」稳得多。

**③ 连带一条测量纪律**：控件**会缩放**时（例如按压时的 0.90 形变），按**固定屏幕半径**取环带会读到假的「变暗」（环随形变内移，固定带只切到外沿）⇒ 先量本帧几何，再**按本帧半径归一**取样，否则「形变」会被误读成「亮度变化」。

### 3.10 `stateStyles` 里**一个状态只能写一个链式属性**

ArkUI 的 `stateStyles` 用的是**链式样式对象**语法（不是键值对）：

```ts
.stateStyles({
  normal: { .backgroundColor(Color.Transparent) },
  pressed: { .backgroundColor(rowPressedSurface()) }
})
```

看着像普通对象字面量，于是很自然会写：

```ts
normal: { .backgroundColor($r('app.color.x')), .opacity(this.interactive ? 1 : 0.5) }   // ❌ 编译失败
```

报错是 `An object literal cannot have multiple properties with the same name` + `.stateStyles doesn't conform standard`——**两句话都不提「一个状态只能一个属性」**，很难从文案反推。

**为什么既有先例帮不上忙**：工程里已有的 `stateStyles` 全是**单属性**，照着它抄「逐字一致」时，你只会比对 `pressed`，不会意识到 `normal` 多写了一个属性。

**修法**：一个状态写一个属性；需要多个效果时，**未声明的属性会回落链式**（`stateStyles` 是**逐属性覆盖**、不是全接管）。

**判据**：写完先搜一遍「逗号 + 链式调用」的多属性写法，再构建。

### 3.11 径向渐变光斑 `radius` 必须 ≤ 中心到最近边缘的距离

**现象**：光斑超出组件边界时颜色在边界处不收敛为全透明；若再叠加 `blur`，会出现可见矩形边缘（**光晕变方框**）。

**修法**：渐变画布用正方形，`center = [w/2, h/2]`、`radius` 略小于半宽、末端色用全透明；要椭圆 / 定位再叠加 `scale` + `translate`，**不要加 blur**。

### 3.12 玻璃材质顶缘的「细条亮线」

**现象**：`ImmersiveMaterial` 开 `lightEffect` 或手写 rim light（1px 高亮行），都会在玻璃胶囊顶缘合成一条**锐利贯穿亮线**。

**修法**：两者都不用；光感改由控件的按压态（`scale` + `brightness`）承担。

### 3.13 遮罩压暗会把「本来同色的两个面」变成「有细线的两个面」

**现象**：侧栏面板与原生顶栏本色同色时，遮罩只压到内容侧 ⇒ 面板右边缘出现竖向色差线；深色下相邻内容近黑、面板偏亮，观感就是「深色下面板发灰」。

**根因**：不是模糊 API 的问题，是**遮罩只覆盖了一侧**。

**定位手段**：逐像素剖面比**三个值**——面板本色 / 内容侧 / 那个「同色参照物」的本色。别凭肉眼先怀疑模糊参数。

## 4. 导航栏与沉浸

> **导读**：框架标题栏的**几何是常量级的**，而且这些常量「从窗口顶算起」而不是「从状态栏之下算起」。本章所有坑都能用一句话概括：**先 dump 出 bounds，再谈怎么写**。

### 4.1 `NavigationTitleMode.Mini` 的 56vp **从窗口顶 y=0 起算**，状态栏会把它吃掉

**现象**：把页面标题栏从 `Full` 改成 `Mini`（理由：「已无自绘栏，官方标准标题栏就是 56vp」），结果**标题栏里的功能钮直接压在状态栏的时钟上**，整条栏几乎不可用。

**真机实测（同一页、除 `titleMode` 外一切相同，状态栏 46vp）**：

| 档 | 框架给的标题栏 bounds | 状态栏之下**可用**高度 |
| --- | --- | --- |
| `Full` | 从状态栏底开始，下沿约 112vp | **约 65.5vp** ✅ |
| `Mini` | 同样从状态栏底开始，但下沿按 56vp 从**窗口顶**算 | **约 9.7vp** ❌ |

**根因**：两档的标题栏**顶边都在状态栏底**，而**底边按该档的常量从窗口顶 y=0 起算**：

- `Full`：112vp 从窗口顶算 ⇒ 扣掉状态栏还剩约 65.5vp；
- `Mini`：56vp 从窗口顶算 ⇒ 扣掉状态栏（46vp）**只剩约 10vp**。

⇒ `Mini` 并不是「状态栏之下的 56vp」，而是「**窗口顶起的 56vp**」。**这不是「矮」，是根本放不下。**

**关键推论（最容易搞反）**：症状是「栏里的控件压住了状态栏」，但**病根与栏里放了什么无关**。实测里构造器已经只剩两枚按钮、零自绘层，仍然只剩 29px ⇒ 「把自绘栏删掉就能用 `Mini`」是错的：**只要状态栏 ≥ 10vp，`Mini` 在任何构造器下都不可用。**

**正确做法**：需要「常驻钉住 + 落在状态栏之下」时用 **`Full`**，接受它的 112vp（比官方「标准」标题栏高，但这是系统给的可用槽位）。

### 4.2 `Navigation` 标题栏构造器的**顶边由框架锚定**，行高只决定栏内控件的中心

**现象**：同一台机器上，两个页面的标题与按钮，一个比另一个**低 27px**。

**根因**：`Full` 档的槽高度是常量，框架把**构造器的顶边锚定**在一个固定位置（与行高无关）⇒ 行高只决定行内控件落在哪：

```text
控件垂直中心 y = 构造器顶边 + 行高 ÷ 2
```

⚠️ 两个容易误判的点：

- **不是 `barStyle` / 背景效果造成的**——那些只改背景层，一行布局都不动；
- **`Row` 报出来的 bounds 可能是被槽裁剪后的**（比实际行高矮），但**行内控件仍按未裁剪的行高居中** ⇒ **只看报出来的 bounds 会漏掉这几十像素的差**。

**修法**：要若干页的标题栏**视觉等高**，就得让它们的构造器**行高相同**（统一走同一套尺寸令牌）。只改内边距 / `justifyContent` / `alignItems` 都改不动中心。

### 4.3 标题栏的**可用高 = 112 − 状态栏**，请求更高会被钳成同一个值

**实测（`titleMode: Full`，状态栏 46vp）**：

- 框架标题栏 = 窗口顶起 **112vp** ⇒ 它**含状态栏那 46vp**；
- 构造器**请求 66vp** 与**请求 56vp**，转储**落点完全相同** ⇒ 可用高只有 **112 − 46 = 66vp**，写更高只是被钳；
- 在 `Full` 下**做不到**「栏内一行贴屏幕顶 y=0」：横向控件必然落在标题栏区间内，比「自绘悬浮顶栏」低约 30px——这是「进框架标题栏」的**固有代价**，不是参数写错。

**推论（判据怎么写）**：

1. 需要给框架标题栏让位的场景（例如容器容器），让位量要按**框架栏在状态栏之下的高度**算（`状态栏 + (112 − 状态栏)`），而不是按自己那一行的高；否则首行会落进框架栏的模糊区；
2. 「覆盖高度有没有回退」必须用**屏幕绝对 px** 比；
3. 不要用 `Mini` 去省高度（见 4.1）。

### 4.4 `scrollEffectOptions` 的滚动遮罩**越过标题栏向下延伸**

**现象**：标题栏下方紧贴一行自建浮层。配上 `NavigationTitleOptions.scrollEffectOptions`（渐变模糊）后，用户一滚动，**那行字就被洗成半透明**；不滚动时是清晰的。

**根因**：框架会为这个滚动效果生成一层遮罩节点，真机实测它的**底边比标题栏底边多出约 96px**，那一带正好盖住紧随其后的自建浮层；遮罩画在内容层**之上**，于是把浮层里的文字一起糊掉。

**量化**（同一页面、同一滚动位置，只差这一条配置；`glyph` = 文字最暗 0.5% 的均值）：

| | 静止 | 滚动后 |
| --- | --- | --- |
| 留着 `scrollEffectOptions` | glyph 102.2 | glyph **141.9** ❌ |
| 删掉它 | glyph 102.4 | glyph **104.5** ✅ |

⚠️ **判「字有没有被洗淡」要看 glyph 值，不要看对比度**：背后内容一变，背景亮度跟着变，对比度会自己动，会被误读成文字问题。

**修法**：标题栏**下方还有自己的浮层**时，不要用 `scrollEffectOptions`；改用标题栏的 **`backgroundEffect`**（常驻模糊，不生成向下越界的遮罩）。两者是**互斥的取舍**：前者是「滚起来才糊」（适合栏背后本来没内容的页面），后者是「一直糊」（适合栏背后一直有内容的页面）。

### 4.5 底部 TabBar 的材质入口与标题栏不是同一个 API 面

见 3.4。补充一条：**「同一个位置」不等于「同一个 API 面」**——通用属性上的 `systemMaterial` 挂在内容根上，而弹层 / 底栏走的是各自 options 里的字段入口；两者在同一个视觉位置上可以有完全不同的生效结论。**排查「官方材质为什么不生效」时，先分清你用的是哪个入口。**

## 5. 终端与流式

> **导读**：终端的难点不在「画出来」，而在**看不见的边界**（回看、resize、宽字符、组合输入）。流式的难点不在「收到数据」，而在**合并与刷新时机**。本章的建议统一是：把语义做进纯函数，用断言锁住边界。

### 5.1 终端仿真内核不要依赖 UI 框架 —— 否则边界永远测不到

**做法**：把「字节流 → 屏幕网格」做成完全不引用 ArkUI / Kit 的纯模块（本项目为 `vt/`：宽度表、样式池、行、缓冲、转义序列状态机、按键映射），渲染层只负责把网格画到 Canvas。

**收益**：回看取行、`resize` 不变量（光标随内容、收缩进回看区、扩张可逆）、宽字符占位、备用屏切换这些边界，全部可以在 Node 里用几万条断言锁住，**不需要设备**；渲染与仿真也能分别演进。

**代价**：转义序列的覆盖面与性能优化都归自己维护。

### 5.2 只有一个主按钮时，「运行中怎么发消息」靠的是 IME 动作

**现象**：上游 Android 输入区只有一个主按钮：运行时状态属于运行中 / 等待审批时显示**中断**，否则显示**发送**。照搬按钮逻辑就会导致「Agent 跑起来之后只能等它跑完」，**而且没有任何报错**——因为发送入口本来就该是**输入法的发送动作**。

**修法**：把 IME 动作接上：

```ts
TextArea({ ... })
  .enterKeyType(EnterKeyType.Send)
  .onSubmit(() => { if (this.canSend()) { this.send(); } })
```

**判据**：真机可以用 `uitest uiInput keyEvent 2054`（回车）触发 `onSubmit` 来验证。

### 5.3 终端 IME 组合态：候选串不能写进 PTY

**现象**：中文 / 日文输入法在组合态下，候选串会被逐字符送进终端，屏幕上出现一堆拼音碎片。

**修法**：把 `onWillInsert` 当作**唯一可信的上屏通道**；退化为「输入框累积 + 回车整段送入」。同时把**输入草稿按会话持久化**（杀进程重启后恢复）。

### 5.4 终端错误要**原文上屏**

**现象**：终端页出错时只显示自造的「出错」两个字，真正的错误信息一个字都不显示——这是最难诊断的一类问题。

**修法**：把服务端 / 内核返回的错误原文直接显示出来；自造文案会让问题无法定位。

### 5.5 流式渲染必须持有内核写入的**活对象引用**

**现象**：流式输出时，界面在动，但内容是旧的 / 不完整。

**根因**：把每帧数据**拷一份**再更新，拷贝发生在写入之前，或者持有的是快照而不是内核正在写的那份引用。

**修法**：持有内核写入的**活对象引用**再触发刷新；收尾的 `flush()` 必须真的被调用（用断言锁住，别只写在注释里）。

**附带**：非 2xx 响应的 `statusCode` 可能为 0；`content` / `finish_reason` 这类字段可能是 **`null` 而不是 `undefined`**——判空要同时覆盖两者。

### 5.6 高吞吐下不要逐条渲染

**做法**：会话实时事件按约 34ms 的窗口**合批**后再通知 UI（≈30Hz），时间线合并做 **upsert-only**（同 id 覆盖，不追加、不重排）。配合增量投影，保证「增量结果 == 全量重算结果」（这条等价性本身就该是一条断言）。

### 5.7 终端回看与 resize 的两条不变量

| 不变量 | 含义 |
| --- | --- |
| 光标随内容 | 键盘开合改变网格尺寸时，光标跟着内容走，不跳到别的行 |
| 收缩进回看 / 扩张可逆 | 行数变少时多出来的行进回看区；变多时能原样拉回 |

这两条都是**纯函数级**的性质，写成断言比截图对比可靠得多。

## 6. 构建与告警

> **导读**：在「零告警」标准下，告警本身就是信息。本章讲两件事：**怎么不被告警逼着写坏代码**，以及**怎么识破「假成功」的构建与命令**。

### 6.1 被静态检查判为「可能抛异常」的 API，必须显式 `try/catch`

**现象**：追求「零 ArkTS 告警」的工程里，取屏幕尺寸这一行会直接破坏标准：

```text
ArkTS:WARN File: …Screen.ets:105:29
 Function may throw exceptions. Special handling is required.
```

**修法**：显式处理并给兜底值，**不要**为了让告警清零而删掉必要的调用：

```ts
try {
  const metrics = display.getDefaultDisplaySync();
  const density = metrics.densityPixels > 0 ? metrics.densityPixels : 1;
  this.imageMaxWidth = Math.floor((metrics.width / density) * 0.72);
} catch (error) {
  this.imageMaxWidth = 240;   // 兜底值，别让取尺寸失败把页面拖垮
}
```

**同类**：`cryptoFramework` 系列也需要显式异常处理。**结论：告警要清零，但清零的方式是「处理」而不是「回避」。**

**判据**：构建日志里告警出现次数为 0。

### 6.2 有些告警消不掉，那就**如实记录**它

**现象**：某些「所有设备都支持」的系统能力调用，即使外面包了 `canIUse(...)` 守卫，静态检查**仍会报**「该 API 并非所有设备都支持」——这是静态检查对「闭包 / lambda 内调用」的局限，不是代码写错了。

**修法**：保留运行期 `canIUse` 守卫 + 在工程文档里记录「这是一条已接受的告警」，**不要为了清零告警而删掉守卫**。

**判据**：接受清单必须有理由、有位置；「清零」不能以牺牲运行期安全为代价。

### 6.3 `canIUse` 是 ArkTS 全局内置函数，不要 import

**现象**：`import { canIUse } from '@kit.BasicServicesKit'` 直接编译报错（`'canIUse' is not exported from Kit`）。裸用即可，**任何 import 都不要加**。

### 6.4 HSP 型 kit 一律运行期 `dynamic import`

**现象**：某个 kit 的实现挂在系统侧的独立 HSP 包上。只要页面（或其任意上游静态 import）引到它，页面创建阶段就直接崩：

```text
LastFatalMessage: [LoadJSPandaFile] load hsp failed, hsp name: …
```

**而且 `canIUse('SystemCapability.…')` 仍返回 true**——**syscap 检测 ≠ HSP 存在**，不能用它做保护。

**修法**：HSP 型 kit 一律**不进运行时导入图**；需要时用运行期 `await import('@kit.X')` + `canIUse` + 全捕获，并准备降级路径。

**判据**：新引入一个 kit 前，先确认它是「打包进应用」还是「系统侧 HSP」；后者必须动态导入。

### 6.5 三种「假成功」

| 形态 | 表现 | 怎么识破 |
| --- | --- | --- |
| **构建命中缓存** | 打印 `BUILD SUCCESSFUL`，但编译阶段是 `UP-TO-DATE`——**根本没编译** | 看编译阶段是否真的执行了；对比产物时间戳与内容 md5 |
| **外部命令退出码为 0 但失败** | 安装 / 取文件失败并打印错误，**退出码仍是 0** | 不以退出码为唯一判据，回读设备上的实际状态 |
| **路径被拼接** | 传绝对路径给工具，被拼成「工作目录 + 路径」而失败 | 用平台原生的路径形式；失败时先打印实际执行的命令 |

**另一条同源**：打包阶段会调用 `java`，`PATH` 里没有 JDK 时报 `spawn java ENOENT`——**而它可能在你「构建成功」很多次之后才第一次出现**（因为前面几次都没真正重新打包）。

### 6.6 构建是**共享可变状态**，并发构建会互相覆盖

**现象**：两个终端 / 两个进程同时跑构建，最坏情况是「本次报成功，但产物其实是上一次的」。

**根因**：构建缓存目录与产物目录都是共享可变状态。

**修法**：构建走**串行化脚本**（文件锁 → 构建 → 校验产物存在 → 计算 md5）。等锁超时用一个**独立的退出码**表示，避免被误判成构建失败。

### 6.7 构建期类型检查的盲区

**做法**：加一个**构建期探针文件**，显式引用各层模块。否则「某个文件因为没有调用点而逃过 `assembleHap` 的类型检查」这件事会一直存在——它编译得过去，因为压根没被编译。

## 7. 验证方法与判据

> **导读**：本章不是「怎么修」，而是「**怎么知道自己修对了**」。这类静默失效的问题，最容易的失败模式不是修不好，而是**用了一个什么都证明不了的判据**，然后宣称通过。

### 7.1 合成事件会**假 PASS**：关键动作必须真实触摸 + 效果回读

**现象**：自动化脚本用合成事件（`dispatchEvent`）驱动点击，一路「通过」，而真人点不动——因为**合成事件不经过命中测试**，全屏遮罩、铺满的兄弟容器都挡不住它。

**修法**：

1. **关键动作补一次真实触摸**（如 `uinput -T -c x y`），再回读结果；
2. 全屏遮罩类缺陷要**成对处理**：官方抽屉的遮罩常常是抽屉本体的**兄弟节点**（`position:fixed`、整屏、半透明黑、`pointer-events:auto`）。只给本体 `visibility:hidden` ⇒ ① 整页被压暗（实测白色 `255→153`，正好乘 0.6）；② **页面所有真实触摸被它吃掉**。修法是扫本体的兄弟节点，按「固定定位 + 覆盖大半视口 + 深色半透明底 + 内部无可交互内容」的特征一起隐藏；**兜底把外壳交还官方时要一并摘掉标记**，否则兜底路径会被自己打瞎。

**判据**：**凡是「必须能被点到」的元素，判据里必须有真实触摸这一条。**

### 7.2 `dumpLayout` 只导出**可见节点**

**现象**：排查「当前会话没有高亮」时，dump 里 8 个会话行的无障碍描述**全是「会话」、没有「当前会话」**，据此判定「状态没回填」——**结论是错的**。真因是：**那一行当时不在可见区，它根本没被 dump 出来。**

**用「读不到某个值」去推「状态没更新」，前提是目标节点确实在可见区**——这个前提不成立时，结论完全无效。

**正确姿势**：

- 判「某行 / 某元素的状态变没变」→ **先让它可见**（滚动 / 展开 / 确保在首屏），再读；
- 或改用**像素 / 颜色回读**、**原生日志**这类**不依赖可见性**的判据。

### 7.3 无障碍字段**不是**稳定的动态状态判据

零成本定标实验（真实触摸 + dump，产物不变）：

```text
进入选择模式、未勾选：  13 × "未选"
真实触摸勾选一行之后：  12 × "未选" + 1 × "已选"     ← 字段确实随状态更新了
```

但同一段代码在另一条路径上（行被**复用**而不是**重建**）会停在旧值，而视觉高亮已经是新的。⇒ 结论：

- 无障碍字段能否反映当前状态，取决于**该元素这次有没有被重建**，而重建时机在不同设备 / 不同交互路径下可能不同；
- **动态状态（选中 / 激活 / 加载 / 禁用）一律用像素 / 颜色回读或原生日志**；无障碍字段适合断言**静态属性配没配**，或在**能确认元素被重建**时做辅助判据；
- 用 dump 做任何回读前，**先确认目标节点在可见区**。

### 7.4 验收夹具要按**请求参数**返回，别用一个罐头响应应付所有路径

**现象**：真机上点文件 `package.json`，弹出的预览却是 `README.md`——看起来像「应用点错了行」，实际是模拟服务端无论请求什么路径都返回同一份写死内容。**这类夹具骗的不是功能，是证据**：截图能证明「有内容」，却证明不了「内容对」。

**做法**：

1. 夹具对同一接口的不同参数**返回必须不同**（例如给 mock 写一棵刻意覆盖不同语言 / 类型的虚拟文件树）；
2. 把每次请求的**入参**记下来，验收时断言「应用请求的正是我操作的那个对象」，而不是只看屏幕；
3. 做不到按参数返回的部分，必须在验证文档里**写明这是罐头数据**，别当成通过。

**同源的一条**：**写接口必须真的回写状态**（`PATCH`、归档、标记已读等）。否则「应用没刷新」与「服务端没存」在证据上无法区分——很容易写下错误结论。

### 7.5 判据要先让**基准读数符合已知事实**

**现象**：用「整宽 y 带的均值差」衡量分界强度时，用户认可的基准页（明确无分界）也算出 **+14.60**。

**根因**：采样口径把标题栏里的大字算了进去。

**修法**：改采样口径（只用左右最边缘的纯底色竖条）直到**基准页读数≈0**，再去量其它页。

**推广**：任何新建的量化判据，第一步都是**拿一个已知答案的样本去标定**。标定不通过，判据无效——不是「目标页有问题」。

### 7.6 「跑过了」不等于「验证到了」：用变异测试证明断言会红

**现象**：某个源码闸门判据恒真——不管实现怎么写都通过，于是它**什么都没检验**，却长期显示绿色。

**修法**：

1. 判据写**紧口径**（约束到具体位置 / 具体常量），不要写「大致存在」；
2. 关键断言配**变异测试**：故意改坏实现，确认断言**确实失败**，且断言里同时校验「变异后的值与原来的不同」；改回实现，确认恢复绿色；
3. 这类变异组应当随套件一起提交（本项目的多个套件里都带 3~5 组变异）。

### 7.7 证据分级：模拟器不等于真机

| 判据类型 | 模拟器 | 真机 |
| --- | --- | --- |
| 有没有渲染、几何与相对明暗 | ✅ 可用 | ✅ |
| 材质 / 观感 / 手势条压线 / 状态栏遮挡 | ❌ 不可作为结论（部分系统约束在模拟器上不生效） | ✅ 唯一可信 |

**结论如实标注**：用模拟器得到的结论，就写「模拟器可见 / 真机未验证」，**不要**放宽成「已验证」。

## 8. 判据速查

| 你要判断的事 | 用什么 | 不要用什么 |
| --- | --- | --- |
| 状态变化有没有驱动 UI | 在 `build()` 里搜该变量名；像素回读 | 看代码里有没有赋值 |
| 列表为什么没更新 | 检查 `ForEach` 的 key 是否含会变字段 | 重启应用「试试」 |
| 元素在哪 | `dumpLayout` 的 bounds（注意：只导出可见节点） | 截图目测坐标 |
| 控件为什么点不到 | 父链上的 `hitTestBehavior`；重叠布局的铺满兄弟 | `clickable=true` 就当没问题 |
| 材质 / 模糊有没有生效 | 开关前后逐像素 MAE；非文字行的最大行间跳变 | 肉眼；代码里写没写 |
| 字有没有被洗淡 | `glyph`（文字最暗 0.5% 的均值） | 对比度（背景一变它就动） |
| 标题栏几何 | dump 出来的 bounds（注意被槽裁剪） | 按文档常量推算 |
| 构建是不是真的重编了 | 编译阶段是否执行；产物 md5 | 只看 `BUILD SUCCESSFUL` |
| 命令是不是真的成功了 | 回读目标状态（退出码不可信） | 只看退出码 |
| 断言有没有真的在检验 | 变异测试（改坏了会红吗） | 它现在是绿的 |
