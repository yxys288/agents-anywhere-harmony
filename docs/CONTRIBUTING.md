感谢你愿意参与 aa-hm（Agents Anywhere 鸿蒙客户端）。本文说明**怎么提一个能被顺利合入的改动**。

## 1. 开始之前

1. 先读 [README.md](../README.md) 了解项目定位与已知限制，读 [docs/ARCHITECTURE.md](ARCHITECTURE.md) 了解分层；
2. 如果是较大的功能或结构性改动，**先开 issue 讨论**，避免写完才发现方向不一致；
3. 提交前请确认你的改动没有把**本机私有信息**带进仓库（见下文「不要提交的内容」）。

## 2. 开发环境

按 [docs/DEVELOPMENT.md](DEVELOPMENT.md) 搭好 DevEco Studio + API 26 SDK + 一台设备或模拟器。

## 3. 分支与提交

### 3.1 分支命名

从 `main` 切出，用 `<类型>/<简短描述>`：

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `feat/` | 新功能 | `feat/terminal-text-selection` |
| `fix/` | 缺陷修复 | `fix/composer-keyboard-avoid` |
| `refactor/` | 不改变行为的重构 | `refactor/timeline-projection` |
| `docs/` | 只改文档 | `docs/api-spec-typo` |
| `test/` | 只改测试与工具 | `test/vt-resize-invariant` |
| `chore/` | 构建、配置、依赖 | `chore/build-script-env` |

描述用小写英文与连字符，尽量简短。

### 3.2 提交信息

采用 Conventional Commits 风格，**首行 ≤ 72 字符**：

```text
<type>(<scope>): <subject>

<body：为什么这么改、有什么取舍>

<footer：关联 issue，如 Refs #12>
```

`type` 用上面分支表里的类型；`scope` 用模块名（`api` / `store` / `vt` / `ui` / `session` / `terminal` / `files` / `docs` / `tools`）。示例：

```text
fix(vt): 备用屏切换时保留主屏回看区

切到备用屏时回看区被一并清空，退出备用屏后历史丢失。
改为两套缓冲各自持有回看区，切换只交换当前视图。
```

约定：

- 一次提交只做一件事，不要把格式化、重命名和功能改动混在一起；
- 提交信息写「**为什么**」，代码已经说明了「是什么」；
- 不要提交生成物（`entry/build/`、`.hvigor/`、`oh_modules/`、`*.hap`）——它们已在 `.gitignore` 里。

## 4. 代码风格

### 4.1 基本约定

- **ArkTS 静态类型**：显式标注参数与返回值类型（工程里所有公开方法都有类型）；不用 `any`，不用动态属性访问；
- 命名沿用上游与现有代码：类 / 枚举用 `PascalCase`，方法与变量用 `camelCase`，常量用 `UPPER_SNAKE_CASE`；
- 文件与目录：`.ets` 文件用 `PascalCase`（如 `SessionDetailStore.ets`），与类名一致；
- 缩进 2 空格；不保留行尾空白；文件末尾留一个换行；
- 注释写「为什么」，尤其是**违反直觉的写法**：如果某处看起来「本可以更简单」，请写清楚是什么约束让它必须这样写。工程里大量注释属于这一类，请保持这个习惯。

### 4.2 分层的硬约束

| 规则 | 原因 |
| --- | --- |
| `vt/`、`model/`、`utils/` **不得 import ArkUI / Kit** | 这些模块要被逻辑自测在 Node 里直接加载，一旦引入框架依赖，测试立刻跑不起来 |
| `feature/` 不画 UI、不写组件 | 业务编排与渲染分离，便于单测与复用 |
| `ui/screens/*` 不放业务规则 | 页面只读状态、派发动作 |
| 参与渲染的状态必须在 `build()` 里被读到 | ArkUI 的观察是「读时登记」，没被读过的状态变化不会触发重绘 |

### 4.3 沉浸光感与材质

工程默认使用**官方材质**，但其生效范围受系统版本约束。改动涉及玻璃、模糊、材质时：

- 先确认目标组件**是否在生效范围内**（页面正文里的普通容器不在）；
- 范围外请使用自绘毛玻璃回退，并保持相邻区域的模糊参数逐字一致；
- 判断「有没有生效」用**开关前后逐像素对比**，不要凭肉眼；
- 相关约束与实测口径见 [docs/ARKTS-PITFALLS.md](ARKTS-PITFALLS.md) 的材质章节。

### 4.4 零告警

改动必须保持构建**零 ArkTS 告警**。新增 API 调用若被静态检查判为「可能抛异常」，请显式 `try/catch` 并给出兜底值，而不是加抑制注释。

## 5. 自测要求

### 5.1 必须跑的

```bash
node tools/logic-test/run-all.mjs     # 逻辑自测：退出码 0 = 全绿
node tools/build-locked.mjs           # 构建：BUILD SUCCESSFUL 且零 ArkTS 告警
```

逻辑自测共 36 个套件；其中 2 个依赖开发期的内部性能基线与证据文档，在开源仓库中会**显式跳过（SKIP）**，其余必须全部通过。详见 [docs/DEVELOPMENT.md](DEVELOPMENT.md) 的「逻辑自测」一节。

### 5.2 按改动面追加

| 改动面 | 追加要求 |
| --- | --- |
| 新增 / 修改可单测的纯逻辑（`api` / `model` / `vt` / `utils` / `MarkdownParse` / `SyntaxHighlight`） | **必须**补对应断言；文件名以 `suite-` 开头即会被自动纳入 |
| 协议相关（端点、字段、事件名） | 同步更新 [specs/01-api-spec.md](../specs/01-api-spec.md)，并让模拟服务端与之一致 |
| UI 与交互 | 在设备或模拟器上实际走一遍，附截图；涉及材质 / 观感 / 手势条压线的，需要真机证据 |
| 终端仿真 | 补边界断言（回看取行、resize 不变量、宽字符占位、备用屏切换） |
| 工具脚本 | 保证零第三方依赖；路径用环境变量或相对路径，**不要写死本机绝对路径** |

### 5.3 关于测试的一条纪律

**「跑过了」不等于「验证到了」。** 提交前请自问：这个断言**失败的时候会不会真的变红**？如果一个判据在任何实现下都成立，它就没有验证任何东西。必要时用一次**变异测试**证明它会红（改坏一处实现，确认断言失败，再改回来）。

## 6. 不要提交的内容

以下内容**一律不进仓库**，PR 里出现会被直接要求移除：

| 类别 | 例子 |
| --- | --- |
| 签名与凭据 | 证书、Profile、密钥库文件，以及任何形式的签名口令与访问令牌 |
| 本机私有配置 | 含本机绝对路径与加密口令的 `build-profile.json5`（用 `build-profile.example.json5` 生成自己的那份） |
| 设备标识 | 真机序列号、设备 UDID |
| 构建产物与缓存 | `entry/build/`、`.hvigor/`、`oh_modules/`、`*.hap` / `*.har` / `*.hsp` |
| 个人数据 | 真实账号的截图与日志、含个人目录结构的截图 |

如果你的改动需要一份配置示例，请提交**占位符版本**（例如 `build-profile.example.json5` 的写法）。

## 7. PR 流程

1. **Fork 并从 `main` 切分支**（分支命名见上文）；
2. **本地自测 + 构建**（见上文「自测要求」），确认退出码为 0；
3. **提交 PR**，描述里至少包含：
   - 改了什么、为什么这么改；
   - **怎么验证的**：跑了哪些自测、在什么设备上验证过、有没有覆盖失败路径；
   - 已知的取舍或未覆盖的部分（**如实写**，写「未验证」比写成「已验证」有价值得多）；
4. **等待 review**：维护者可能会要求补断言、补证据或缩小改动面；
5. **review 期间的新改动**：追加提交即可；如果因为 rebase 需要 force-push，请在 PR 里说明这一轮改了什么；
6. **合入**：保持 `main` 可构建、自测全绿。

### 7.1 好的 PR 长什么样

- 改动面小且内聚，diff 里没有无关的格式化；
- 断言与实现一起提交，且断言能证明会红；
- 描述里能看到「我验证了什么、我没验证什么」；
- 涉及界面时附对比截图（改前 / 改后）。

## 8. 沟通

- 缺陷报告请附：应用版本、设备与系统版本、复现步骤、期望与实际结果、相关日志；
- **提交日志前先脱敏**：删掉令牌、账号、设备序列号与本机路径；
- 安全相关问题请不要开公开 issue，先私下联系维护者。
